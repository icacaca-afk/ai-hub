## 逐项反馈（8 个确认问题）

### Q1 unsubscribe() — ✅ 当前 OK，V1.0 建议 Subscription Handle

> 你现在 `handler_id = id(handler)` 实际上没有问题。
> 而且你已经考虑了 bound method 每次访问都会创建新的对象。
> 这说明实现不是随手写出来的，而是理解了 Python 的对象模型。
>
> 但是——如果 V0.9.5 以后 EventBus API 冻结，我更建议：
> `token = bus.subscribe(...)` / `bus.unsubscribe(token)`
> 类似 Qt connect/disconnect、C# IDisposable、Java Subscription。
>
> 原因不是 Python，而是 Subscription 本身就是一个生命周期对象。
> 以后 `subscription.pause() / resume() / close()` 都可以自然扩展。

**结论**：V0.9.4 `id(handler)` 维持。V1.0 可升级为 Subscription Handle（非阻塞，记入路线）。

### Q2 latency — ✅ perf_counter 正确，建议加 latency_source

> 你现在 `perf_counter() → Router.execute() → perf_counter()` 我认为完全正确。
> 因为这是 Runtime 能保证的数据。
> Server latency 其实属于 Provider Metadata，不是 Runtime。
>
> 我的建议反而是：ExecutionMetrics 增加来源 `latency_source`（client / server）。
> 未来可以区分 Client Measured / Server Reported，而不是覆盖。

**结论**：V0.9.4 client-side 测量维持。V0.9.5+ 可加 `latency_source` 字段区分来源。

### Q3 同步 EventBus — ✅ 支持同步，建议 ADR 补一句

> 我仍然支持同步。原因：现在 Runtime 只有 CLI，异步只会增加线程/锁/关闭/Flush/Race 复杂度。
>
> 不过 ADR 我建议补一句：
> **Event handlers should be lightweight and non-blocking.**
>
> 这样 SQLite 以后就知道：不能直接 INSERT，而是后台队列。

**采纳**：补充到 ADR-0017（本次提交）。

### Q4 TraceCollector vs PlanStore — ✅ 不要统一，CLI 负责组合

> 我的观点没有变化。不要统一。
> 但是我建议：不要做 `inspect → Trace Available` 以及 `trace → Inspect Available` 双向引用。
> 这样两个模块会越来越知道彼此。
>
> 我更建议：只有 CLI 负责组合。
> `CLI → PlanStore + TraceCollector`，而不是 `TraceCollector 知道 PlanStore`。

**说明**：V0.9.4 当前 inspect 已显示 "Trace: Available/No Trace"（通过 `TraceCollector.has(plan_id)`，非反向引用）。这是单向查询（CLI 调用两者），符合 ChatGPT 建议。维持现状，不增加反向引用。

### Q5 schema_version — ✅ 赞同维持 "1"

> 我反而认为现在做得很好。不要 `consumer_min_version`。
> 原因：这会变成 Package Version。Schema 不是 Package。
> Schema 回答：JSON 长什么样。不是：谁可以消费。
>
> 保持 schema_version=1 我赞同。

**结论**：维持现状。

### Q6 ExecutionStore（V0.9.5）— ★ 方案 A 最推荐

> 三个方案：
> A: Memory → SQLite Consumer ★★★★★ 最推荐
> B: PlanStore → SQLite + Trace → SQLite ★★★ 容易 Store 越来越重
> C: Everything → EventStore ★★★★☆ 很多大型 Runtime 最后都会走的路，但不是 V0.9，太早
>
> 我建议坚持 A。甚至 ExecutionStore 不要继承 TraceCollector，
> 而是两者都是 EventBus Consumer：
> ```
> ExecutionEvent → TraceCollector → Timeline
> ExecutionEvent → SQLiteExecutionStore → DB
> ```
> 不要 SQLiteTraceCollector，因为 SQLite 不是 Trace，SQLite 只是 Storage。

**采纳**：V0.9.5 走方案 A。SQLiteExecutionStore 作为独立 EventBus Consumer，不继承 TraceCollector。

### Q7 token / cost — ✅ 坚定建议 Provider 不 emit Event

> 这里我建议：不要让 Provider emit Event。这一点我建议非常坚定。
>
> 原因：ExecutionEvent 应该只有 Runtime 产生。
> 否则以后 OpenAI emit() / Claude emit() / Gemini emit()，Event 格式开始漂移。
>
> 正确方式：Provider 返回 `ProviderResult.server_metrics`（token / cost / cache_hit），
> Runtime 收到后统一转换为 ExecutionMetrics。
> Provider 永远不知道 EventBus。这样 Provider 仍然保持纯 Adapter。

**采纳**：V0.9.5+ token/cost 采集走 ProviderResult.server_metrics → Runtime 转换路径。Provider 不接触 EventBus。

### Q8 EventType Filtering — ✅ V0.9.4 OK，未来内部升级

> V0.9.4 完全 OK。未来 V0.9.5 可以升级。
> 但是升级方式：不要改 emit()，而是让 `subscribe(event_type=...)` 真正生效。
> 这样 API 不用变。内部可以 list → dict[event_type] → handlers，非常自然。

**结论**：V0.9.4 维持（subscribe 接口预留，内部不过滤）。未来内部升级，API 不变。

## ⚠️ 唯一建议补充的设计原则

> 我认为现在 Runtime 已经有了 ExecutionEvent，下一步其实应该明确：
> **ExecutionEvent 是不可变（Immutable）的。**
>
> 也就是说：一旦 emit() 以后，Consumer 不能 `event.data["latency"] = ...`，
> 否则多个 Consumer 会互相影响。
>
> 建议 ADR 以后补一句：
> **ExecutionEvent should be treated as immutable after emission.**
>
> 哪怕现在只是约定，不做强制。这是事件驱动架构里一个很重要的约束。

**采纳**：补充到 ADR-0017（本次提交）。

## V0.9.5 方向（ChatGPT 建议）

> 我认为 V0.9.5 不应该追求更多功能，而应继续围绕事件驱动模型扩展，
> 例如 SQLite 持久化、指标采集和历史记录都作为 ExecutionEvent 的消费者实现，
> 而不是重新侵入 Executor。
> 这会让 V1.0 之前的架构保持一致且易于维护。

**结论**：V0.9.5 = SQLiteExecutionStore（方案 A，EventBus Consumer），不侵入 Executor。
