## 逐项反馈（8 个确认问题）

### Q1 SQL 注入风险 — ✅ 参数化充分

> 全部参数化（`?` 占位符 + `IN (?, ?, ?)`），没有 SQL 注入问题。
>
> 我不会为了 6 个 Optional 参数去引入 SQLAlchemy。
> 反而：SQLAlchemy 会让这一层更复杂。
> SQLiteExecutionStore 本来就是轻量 Store，保持 sqlite3 即可。

**结论**：维持参数化 sqlite3。

### Q2 provider=[] 返回空 — ✅ 赞同

> `provider=[]` 本质上表示 `provider IN ()`，SQL 本来就是空集合。
> 所以 `[] → []` 是最自然的语义。
> 没必要 `ValueError`，否则 CLI 以后还得特殊处理。

**结论**：维持 provider=[] 短路返回空 list。

### Q3 list_plans 混合实现 — ✅ 合理取舍

> 我认为你的取舍合理。
> 很多人容易掉进一个坑：为了统一而统一。
>
> 实际上 SQLite 本来就擅长 `COUNT / GROUP / MAX / MIN`。
> 所以适当利用 SQL 聚合没有问题。
>
> 我的原则一直都是：
> - Storage 负责 Storage
> - Analytics 负责 Analytics
> - 不是 SQL 什么都不能做

**结论**：维持 query_events + 单条 SQL 聚合的混合实现。

### Q4 dataclass vs Pydantic vs NamedTuple — ✅ dataclass 最合适

> 完全合适。甚至比 Pydantic 更合适。
>
> 原因：
> - ExecutionStatistics 没有 Validation，只有 Aggregation
> - dataclass 是 Python 官方推荐
> - NamedTuple 反而以后不好扩展

**结论**：维持 dataclass。

### Q5 大量 events 性能 — ✅ 不要提前优化

> 目前 540 tests / 单进程 CLI，远远不到需要 Streaming Analytics 的程度。
>
> 所以一次 list → compute() 完全够。
> 以后几十万 Event，再 Iterator / Generator / Chunk 都来得及。
> **不要提前优化**。

**结论**：维持单次遍历。

### Q6 时间戳损坏 — ⚠️ 唯一可选改进（不是必须）

> 这里我唯一建议补一个很小的健壮性增强。
>
> 目前如果 timestamp 损坏：
> - 建议 StatisticsCollector 抛异常改为：warning + 跳过该条 latency
> - 坏一条 Event 不影响整个统计
> - 这是 Analytics 常见的容错策略
>
> 不是必须修改。但 V1.0 可以考虑。

**结论**：V0.9.7 维持现状，V1.0 再补 try/except + warning。当前实现已经有 try/except（解析失败时跳过 latency），已部分采纳。

### Q7 CLI 参数解析 — ✅ 赞同手写

> 我反而支持目前手写。
> 因为参数只有 `plan / provider / since / until / json`。
> 没必要 argparse 再套一层。
> 除非以后几十个参数，否则保持简单。

**结论**：维持手写 while 循环。

### Q8 est. 标注 — ✅ 完全赞同

> 我看到你已经统一采用 `est.`，这比 `≈` 更稳。
> Windows / PowerShell / CMD / UTF-8 历史上一直存在兼容性差异。
> 统一 `est.` 更符合 CLI 工具定位。

**结论**：维持 "est." 标注。
