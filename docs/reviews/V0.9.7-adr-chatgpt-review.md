## 总体结论

> ADR-0020：APPROVED（Proposed）
> 评分：9.95 / 10
>
> 整体来看，我认为 ADR-0020 是 V0.9.x 最自然的一步。
>
> 如果说：
> - V0.9.4 建立了 ExecutionEvent（事实）
> - V0.9.5 建立了 ExecutionStore（持久化）
> - V0.9.6 建立了 ExecutionMetrics（观测）
>
> 那么 V0.9.7 正是在建立 **Query Layer（分析）**。
>
> 这也是 Event Sourcing 系统最典型的演化顺序：
> `Event → Store → Query → Analytics`
>
> 你的 ADR 与这个演化方向是一致的，没有出现把 SQLite 慢慢做成 Workflow DB 的倾向，这一点非常重要。

### 核心认可（三点 ★★★★★）

#### ① query_events() 成为唯一查询入口

> 真正重要的其实不是 stats。
> 真正重要的是：
>
> ```
> ExecutionStore
>     └── query_events(...)
>              ├── history
>              ├── stats
>              ├── future export
>              ├── future replay
>              ├── future debugger
>              └── future dashboard
> ```
>
> 以后所有东西都建立在 `query_events()`，而不是 `get_events()` / `list_plans()` / `get_provider()` 越来越多 SQL。
>
> 这个方向完全正确。

#### ② StatisticsCollector 独立

> 不要 `SQLiteExecutionStore.compute_statistics()`，否则 Storage 开始知道 Analytics。
>
> 应该是：
> ```
> Storage → query_events() → StatisticsCollector → ExecutionStatistics
> ```
>
> 完全符合单一职责。

#### ③ stats 完全来自 Event

> 这是 ADR 最大的亮点。
>
> 不是 `PlanStore → Stats`，而是 `ExecutionEvent → Statistics`。
>
> 以后 Runtime 再复杂，Statistics 不用改。

## 逐项反馈（8 个确认问题）

### Q1 query_events 参数设计 — ✅ 完全够，不要 QueryBuilder

> 现在这样（plan_id / provider / event_type / step_id / since / until / limit）完全够。
>
> 不要现在引入 QueryBuilder。原因很简单：
> - 目前查询复杂度：只有 AND
> - 没有 OR / NOT / GROUP / HAVING / ORDER BY / JOIN
> - 所以 DSL 没有任何收益
>
> 等 V1.x 真出现 `(provider=A OR provider=B) AND latency>1000 AND status=failed` 再设计 QueryBuilder。
> 现在会明显过度设计。

**结论**：维持 6 个 Optional 过滤参数 + limit。

### Q2 list_plans 是否保留 — ✅ 保留，但文档写清楚 Convenience API

> 保留。但是：文档写清楚 `Convenience API, implemented via query_events()`。
>
> 不要让用户误认为 `query_events()` 和 `list_plans()` 是两套查询系统。
> 它应该只是 `query_events() → list_plans()` 的 helper。

**采纳**：在 ADR-0020 决策 2 明确 list_plans 是 Convenience API。

### Q3 StatisticsCollector 是否独立 — ✅ 支持，未来可拆子模块

> 我支持。甚至建议以后：
> ```
> planner/statistics/
>     collector.py
>     models.py
>     formatter.py
> ```
>
> 以后统计会越来越多，最好不要都塞一个 statistics.py。
>
> 但 V0.9.7 不需要。

**结论**：维持单文件 `planner/statistics.py`，未来再拆。

### Q4 trace 不统一 — ✅ 最赞同的取舍

> 这是我最赞同的一个取舍。
>
> 很多项目喜欢"统一接口"，于是 Memory / SQLite / Redis 全部实现 query_events()，最后为了统一而统一。
>
> 实际上 TraceCollector 根本不是 Store，它只是 recent event cache，所以它没有义务实现 query_events()。
>
> V1 如果 Memory Event Store 真的出现，再统一。

**结论**：维持决策 7（trace 不重构）。

### Q5 是否加入 P95 — ✅ 不要

> 不要。原因不是实现复杂，而是：现在样本数量太小。
>
> CLI：几十 / 几百 / 几千 Event，P95 意义有限。
>
> 以后 Dashboard / 长期运行 / 几百万 Event，再 P50 / P90 / P95 / P99 更合理。

**结论**：维持 V0.9.7 只算 avg，P95 推迟 V0.9.8+。

### Q6 float 是否继续 — ✅ 继续

> 继续。因为现在 cost 只是 estimate，甚至 OpenAI Provider 返回的 token 不是真正账单。再 Decimal 意义有限。
>
> 什么时候切 Decimal？我建议：Billing / Invoice / Chargeback 出现时。不是 Statistics。

**结论**：维持 float，V1.0 评估 Decimal。

### Q7 多 Provider 查询 — ⚠️ 唯一建议提前做的小调整

> CLI 目前 `--provider openai` 够。但是接口最好设计成：
>
> ```python
> provider: str | list[str]
> # 或
> provider: Sequence[str]
> ```
>
> CLI 可以仍然单 provider，以后 API 直接支持 `provider=["a","b"]`，CLI 不用变，接口已经准备好了。
>
> 这是我唯一建议提前做的小地方。

**采纳**：query_events() 的 provider 参数类型改为 `str | list[str] | None`，CLI 仍单 provider。

### Q8 范围是否太保守 — ✅ 刚刚好

> 我认为：刚刚好。因为真正重要的是 query_events()，不是 P95 / Decimal / Trend / Histogram。
>
> Analytics 的基础：不是图表，而是统一 Query。你现在正是在补这一层。

**结论**：维持范围。

## ChatGPT 唯一建议补充（0.05 分）

> 我建议 ADR 多写一个原则：
>
> **Analytics Never Mutates Events**
>
> 即 StatisticsCollector 必须满足：
> ```
> ExecutionEvent → ExecutionStatistics
> ```
> 永远 Read Only，不能：
> - 修改 Event
> - 补 Event
> - 缓存 Event
> - 写回 SQLite
>
> 否则以后 Analytics 越来越容易污染 Storage。
>
> 我会在 ADR 加一句：
> **StatisticsCollector MUST be a pure read-only projection.**
>
> 这是 Event Sourcing 很重要的一条原则。

**采纳**：在 ADR-0020 决策 5 增加 Read-Only Projection 原则。

## Runtime Contract 是否现在写

> 我的建议和之前一样。不用阻塞代码。
>
> 但是：我建议 V0.9.7 发布以后，优先补 `docs/runtime-contract.md`。
>
> 甚至：我认为它的重要性已经接近 Provider Contract。
>
> 因为以后 Workflow Runtime / Checkpoint / Replay / Retry / Recovery 全部建立在 ExecutionEvent。如果 Runtime Contract 不稳定，后面很容易 Event 越长越乱。

**结论**：维持 V0.9.7 ADR 决定 — 不阻塞代码，V0.9.7 完成后单独写 Runtime Contract。

## 关键引言

> **Event Sourcing 演化顺序**
> Event → Store → Query → Analytics
> V0.9.7 正是在建立 Query Layer（分析）。

> **query_events 是唯一查询入口**
> 真正重要的不是 stats，而是 query_events() 成为所有查询的基础。

> **StatisticsCollector 是纯 Projection**
> StatisticsCollector MUST be a pure read-only projection.
> 绝不修改 ExecutionEvent，也绝不写回 ExecutionStore。

> **trace 不统一的合理性**
> TraceCollector 根本不是 Store，它只是 recent event cache。
> 没有义务实现 query_events()。

> **Analytics 的基础**
> 不是图表，而是统一 Query。
