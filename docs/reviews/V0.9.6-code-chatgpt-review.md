## 总体结论

> V0.9.6 Code：APPROVED
> 评分：9.98 / 10
>
> 相比 ADR，我更关心的是代码有没有把 ADR 里的边界真正落实。
> 从你给出的实现来看，我认为落实得比较好。
>
> 特别是两点：
> 1. **Provider 仍然不知道 ExecutionEvent**
> 2. **ExecutionMetrics 与 server_metrics 仍然是两层模型**
>
> 这两个边界没有破。

### 核心认可

> V0.9.6 做的是一件很重要但很容易做坏的事情：
> **把 Provider 的运行信息引入 Runtime，而没有让 Runtime 依赖某个 Provider。**
>
> 整个数据流已经变成：
>
> ```
> BridgeResult.raw
>         │
>         ▼
>   MetricsExtractor
>         │
>   server_metrics (dict)
>         │
>         ▼
>   Result.metadata
>         │
>         ▼
>   PlanExecutor
>         │
>         ▼
>   ExecutionMetrics (Runtime)
>         │
>         ▼
>   ExecutionEvent
> ```
>
> Runtime 最终消费的是 **ExecutionMetrics**，而不是 **OpenAI usage JSON**。
> 这是最大的优点。

### 最终评价

> V0.9.6 的代码实现与 ADR 基本一致，没有为了采集 Metrics 去破坏此前建立的 Core Freeze，也没有让 Provider 或 ExecutionEvent 相互侵入。MetricsExtractor、ExecutionMetrics 与 server_metrics 的分层保持得很好，整个数据流依然符合"ExecutionEvent 是唯一执行事实来源"的原则。
>
> 唯一建议在正式合入前调整的是未知模型的价格策略：相比使用 _default 价格估算，我更倾向于返回"未知/不可估算"（例如 0 并配合 estimated=false 或 CLI 显示 Unknown），避免给用户一个看似精确但实际上可能偏差很大的成本数字。除此之外，这个版本已经具备合入条件，我认为可以作为 V0.9.x Runtime Metrics 阶段的完成版本。

## 逐项反馈（8 个确认问题）

### Q1 execute() 复制 30 行（MetricsRouter） — ✅ V0.9.6 可接受（Core Freeze 技术债）

> V0.9.6 可以接受。
> 原因只有一个：现在没有 Extension Point。
> 你不能 `super().execute()` 因为 BridgeResult 已经没了。
> 所以复制 `Router.execute()` 实际上是为了保持 Core Freeze 付出的技术债。
>
> 建议在 ADR 明确写一句：
> **MetricsRouter intentionally duplicates execute() because the current Router API does not expose BridgeResult.**
>
> 不要现在抽。等 Router 以后有 Hook（例如 `_after_bridge()`），自然删除重复。

**结论**：保留当前实现（复制 30 行）。ADR-0019 已包含该说明。未来 Router 暴露 post-bridge extension point 后退出。

### Q2 延迟 import（extractors.py 内部 import pricing） — ✅ 合理，不引入 DI

> 合理。而且我不会为了这个引入 DI（例如 `extract(..., pricing)`），反而 API 越来越复杂。
> 目前 Pricing 只是 Extractor 内部实现。延迟 import 完全可以。

**结论**：保留当前实现（延迟 import）。

### Q3 _HANDLERS dict（不引入注册器） — ✅ 保持 dict

> 会保持 dict。原因：目前只有 OpenAI。以后如果达到 5+ / 10+ Provider，再注册器。
> 现在不要过度设计。

**结论**：保留 dict。**Rule of Three**——等 Provider 数量增加再引入注册器。

### Q4 `except Exception` 容错 — ✅ 合理（Observation 不是 Execution），但 log 加 Exception Type

> 这里我反而支持你。原因：这里属于 **Observation**，不是 **Execution**。
> 例如 `json.loads` 失败，不能影响 Task。所以 `except Exception` 完全合理。
>
> 但是建议 Log 带 Exception Type：
> ```
> extract failed provider=openai_api (JSONDecodeError)
> ```
> 而不是只有 message。以后排查容易很多。

**结论**：**采纳建议**——log 增加 `type(exc).__name__`。

### Q5 _default pricing（未知 model 用默认价格） — ⚠️ 调整：未知 model 返回 0

> 这里我的意见和 ADR 有一点不同。
> 我建议未知 Model 返回 0，不要 _default 价格。
>
> 原因：未知模型意味着你不知道真实价格。如果默认 0.01 / 0.03，很容易误导。
> 例如以后 GPT-5 价格完全不同，用户看到 ≈ $0.02 其实完全错。
>
> 所以我建议：
> - known model → estimate
> - unknown → 0（estimated = false）或 CLI 显示 Unknown
>
> 比：错估更好。

**结论**：**采纳建议**——移除 `_default` 价格条目，未知 model 返回 0.0；新增 `is_known(model)` 抽象方法用于 estimated 标记。

### Q6 `≈` 符号（CLI 显示） — ⚠️ 调整：统一用 "est."

> 这里我建议：Windows 不要赌。
> 建议 CLI 统一 `est.` 例如 `est. $0.0021`，或者 `estimated $0.0021`。
> 因为 CLI 不是 Markdown，兼容性更重要。

**结论**：**采纳建议**——`≈$` 改为 `est. $`（Windows 终端兼容性）。

### Q7 嵌套 JSON（server_metrics 直接存 TEXT） — ✅ 不扁平化

> 这里没有问题。SQLite TEXT。以后 query_events 查询主要按 plan_id / provider / timestamp / type，不是 JSON。
> 而 server_metrics 更多展示。以后如果真要 token > 1000 统计，SQLite JSON1 也可以支持。
> 所以不用提前扁平化。

**结论**：保留当前实现（server_metrics 直接 JSON dump 进 TEXT）。

### Q8 aggregate_metrics（Plan 聚合层） — ✅ 总体正确，V1.0 再考虑 Decimal

> 总体正确。但是建议未来不要用 float，而是 Decimal。不是现在，而是 V1.0。
> 例如 0.0012 + 0.0034 + ... 长期 float 误差一定存在。
> 不过 V0.9.x CLI 影响几乎没有。

**结论**：保留当前实现（float）。V1.0 再评估是否切换到 Decimal。

## ChatGPT 主动补充的设计原则

### 原则 1：ExecutionMetrics 是 Normalized Metrics（推荐写入 ADR）

> 我建议 ADR 增加一句：
> **ExecutionMetrics represents normalized runtime metrics; server_metrics preserves provider-native metrics without interpretation.**
>
> 这是以后支持几十个 Provider 非常重要的一条原则。否则大家容易直接消费 server_metrics。

**采纳**：作为 ADR-0019 原则 E（已有）的强化补充说明。

### 原则 2：MetricsRouter 属于 Compatibility Layer（推荐写入 ADR）

> 我建议现在开始明确它属于 Compatibility Layer。
> ADR 增加：
> **MetricsRouter exists because Router currently discards BridgeResult.raw.**
> **It should disappear once Router exposes a post-bridge extension point.**
>
> 这样以后大家知道它不是永久架构。

**采纳**：ADR-0019 原则 F（已有）覆盖该约束。

### 原则 3：V1.0 不要再新增 CostRouter / TraceRouter / CacheRouter（推荐 ExecutionPipeline）

> 我建议 V1.0 不要再新增 CostRouter / TraceRouter / CacheRouter，
> 而是形成 ExecutionPipeline：
> ```
> BridgeResult
>     ↓
> Result Decorators
>     ↓
> Result
> ```
> Metrics / Trace / Billing 全部 Decorator。Router 重新变瘦。

**采纳为 V1.0+ 方向**：V1.0 设计 ExecutionPipeline（Decorator 模式），不再新增 Router 子类。Router 退出"Metrics/Trace/Billing 收集"职责。
