## 总体结论

> V0.9.5：APPROVED
> 评分：10.0 / 10
>
> 这次和前几次不太一样。
> 我认为 V0.9.5 是 V0.9.x 的收官版本之一。
>
> 不是因为 SQLite，而是因为 Runtime 的整个观察链已经闭环了：
>
> ```
> Task
>    │
> Planner
>    │
> Plan
>    │
> Executor
>    │
> ExecutionEvent
>    │
>    ├── TraceCollector（Memory）
>    ├── SQLiteExecutionStore（Persistent）
>    ├── Future Metrics
>    ├── Future UI
>    └── Future Remote Sync
> ```
>
> 这个结构已经比较成熟。

### 核心认可

> 我重点看的是：SQLite 有没有重新侵入 Runtime。
> 从你的摘要来看，没有。
> SQLite 始终只是：EventBus Consumer，而不是：Executor Dependency。
>
> 这是整个 V0.9.x 最重要的一条架构约束。
> 只要这一条没破，以后 CSV / REST / Telemetry / Prometheus / Cloud 都可以继续作为 Consumer。

### 最终评价

> 从 V0.8 到 V0.9.5，ai-hub 已经完成了从"Provider Router"到"事件驱动 Runtime"的核心架构转型，而且整个过程中保持了 Core Freeze，没有让新的能力侵入 core/、router/ 或 providers/。这一点比新增功能本身更有价值。
>
> 唯一值得保留在后续版本继续关注的是：随着 Consumer 增多，要继续坚持 ExecutionEvent 是唯一执行事实来源、Storage 是派生数据而非真相来源 这两条原则。只要这两条不被打破，后续加入 Token/Cost、统计分析、远程同步甚至 Workflow Runtime，都可以在现有架构上自然演进，而不会导致 Runtime 再次耦合。

## 逐项反馈（6 个确认问题）

### Q1 list_plans 派生（status / step_count） — ✅ 保留当前方案

> 我的建议：现在的方案比 COUNT 更好。
>
> COUNT(step_id) 回答的是"有多少 Event"，不是"Plan 有多少 Step"。
> 例如 step_started + provider_selected + provider_finished + step_finished 同一个 Step，COUNT=4，显然不对。
>
> 所以：如果 planner_finished → step_count 存在，优先使用；否则 Fallback COUNT(DISTINCT step_id)。
> 我不会退回简单 COUNT。

**结论**：当前实现（优先 planner_finished.step_count，回退 COUNT(DISTINCT step_id)）保留。

### Q2 exec-history 命名 — ✅ 保留

> 我其实挺喜欢。因为 history 太泛。
> 以后可能还有 provider-history / router-history / cache-history。
> 而 exec-history 已经说明：这是 Execution。不是 Git History，不是 Shell History。
>
> 唯一建议：CLI Help 可以写 "Execution History"，命令保持 exec-history。

**结论**：命令名保留 `exec-history`；CLI Help 用 "Execution History"（已是这样）。

### Q3 _describe_event 代码重复（trace.py vs history.py） — ✅ 现在不抽

> 这是我唯一认为值得讨论的地方。
> 我的建议：现在不要抽。
>
> 因为很多项目一看到重复 10 行，马上 utils.py，最后 CLI 开始共享各种 Renderer，以后 Renderer 越来越大，越来越难维护。
>
> 目前 trace / history 虽然重复，但职责不同：一个 Memory，一个 SQLite。未来格式很可能不同。
> 所以保持重复，直到真的第三个 Consumer（例如 export），再抽 Renderer。

**结论**：保持当前重复，等第三个 Consumer（如 export）出现再抽 Renderer。**Rule of Three 的应用**。

### Q4 lazy init 的 SQLiteExecutionStore — ✅ 保留 lazy init（创建空 DB）

> 这里我的建议和你略有不同。
> 我仍然建议：创建空 DB。
>
> 原因：SQLite 本身就是 Database，不是 Log。
> 例如第一次 `sqlite3 app.db` 也会创建。用户不会觉得奇怪。
>
> 如果第一次 `ai-hub exec-history` 得到 "Database Created / No Execution History"，我觉得体验很好。
> 而不是报错。因为没有历史不是错误，只是 Empty State。

**结论**：**采纳 ChatGPT 建议**——保留 lazy init（当前实现即如此，`get_execution_store()` 在 None 时自动构造 SQLiteExecutionStore，会创建空 DB）。无需改代码。

### Q5 同步 INSERT 每 event commit — ✅ 坚持每 event commit

> 这里我支持每 Event commit。
> 理由：比性能更重要的是 Crash Safety。
>
> 例如已经 plan_started / planner_started / step_started，如果 Runtime 崩溃，至少 History 还有前面的。
> 如果全部最后 plan_finished commit，那么 Crash 全部丢失。
>
> 所以我会坚持 V0.9.x 每 Event commit。
> 什么时候 Batch？真正 Async Queue 以后。

**结论**：当前实现（每 event INSERT + commit）保留。**Crash Safety 优先于性能**。Batch 推迟到 V1.0+ Async Queue。

### Q6 data 字段 JSON 序列化 ensure_ascii=False — ✅ 没问题，建议补充约束

> json.dumps(..., ensure_ascii=False) 没有问题。
> 真正决定是否可存储的是 Python 的 str。SQLite TEXT 存储的是 Unicode 文本。
> 只要 event.data 已经是 Python 字符串，SQLite 不会因为中文 / 日文 / Emoji 出问题。
>
> 真正需要注意的是：如果 event.data = {"x": bytes(...)} 或者 datetime / UUID / Path，这些 JSON 本身不能序列化。
>
> 所以我建议：不是 UTF-8，而是增加一个约束：
> **ExecutionEvent.data 应仅包含 JSON 可序列化的数据（dict、list、str、int、float、bool、null）。**

**结论**：`ensure_ascii=False` 保留；**采纳建议**——补充 `ExecutionEvent.data` JSON 可序列化约束（写入 ADR-0017 / ADR-0018）。

## ChatGPT 主动补充的设计原则

### 原则 1：Storage is Disposable

> 我建议现在开始明确：**Storage is Disposable**。
>
> 什么意思？SQLite 不是 Source of Truth。ExecutionEvent 才是。
> 所以即使 `rm execution.db`，Runtime 仍然可以运行。Storage 只是缓存，不是 Runtime。
>
> 我建议 ADR 以后可以写一句：
> **Persistent stores are derived from ExecutionEvent and may be recreated at any time.**
>
> 这一句话会让以后 Migration / Backup / Import / Export 都容易很多。

**采纳**：写入 ADR-0018 作为补充原则。

### 原则 2：Event Query 统一（未来方向）

> 现在 SQLite 已经有 Event。我建议以后不要直接查询 Plan（例如 `get_plan()`），而是统一 Event Query：
>
> ```python
> query_events(plan_id=...)
> query_events(event_type=...)
> query_events(provider=...)
> ```
>
> History / Timeline / Statistics 全部派生。
> 这样 ExecutionStore 永远保持 Event Store，不会慢慢演变成 Workflow DB。

**采纳为 V0.9.6+ 方向**：V0.9.7 Statistics 实现时采用 `query_events(...)` 统一查询接口，而非 `get_plan(...)`。

### 原则 3：V1.0 主题聚焦 "Workflow Runtime on Event Model"

> 我建议把 V1.0 的主题稍微再聚焦一点。
> 不是 "Workflow Runtime"，而是 **Workflow Runtime on Event Model**。
>
> 也就是说：Workflow 不是绕过 ExecutionEvent，而是继续发 ExecutionEvent。
>
> 例如：
> - ConditionEvaluated
> - RetryStarted
> - RetryFinished
> - CheckpointCreated
> - ResumeStarted
>
> 都属于 ExecutionEvent。
>
> 这样 Timeline / SQLite / Metrics 完全不用改。这会让 V1.0 的演进非常平滑。

**采纳**：V1.0 ADR 主题定为 "Workflow Runtime on Event Model"，所有 Workflow 事件都是 ExecutionEvent 的子类型。
