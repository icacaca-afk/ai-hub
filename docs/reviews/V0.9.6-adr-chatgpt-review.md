## 总体结论

> ADR-0019：APPROVED（Proposed）
> 评分：9.95 / 10
>
> 这是 V0.9.x 第一次让我觉得需要提醒一个潜在的架构风险，但总体方向仍然是正确的。

### 核心认可

> V0.9.6 做的事情其实只有一句：**把 Provider 返回的运行指标安全地带进 Runtime。**
>
> 如果把整个 V0.9.x 放在一起看，现在已经形成了四层：
> Provider Adapter → Bridge → Router → Execution Runtime → ExecutionEvent → Consumers

### 最终评价

> 我认为 ADR-0019 保持了 V0.9.x 一直以来的设计风格：不修改冻结的核心层，而是在边界之外新增能力。MetricsRouter 在目前的约束下属于一种兼容层，而不是对路由策略本身的修改，因此我认为没有违背 Core Freeze 的精神。
>
> 唯一需要持续警惕的是，不要让 MetricsRouter 演变成一个不断叠加执行增强逻辑的"万能 Router"。建议在 ADR 中明确它的职责边界和临时性质，把它定位为在不修改 Router 的前提下，为 Runtime 补充 Provider 指标的适配层。

## 逐项反馈（8 个确认问题）

### Q1 Router 子类化是否违反 Core Freeze — ✅ 不违反，但走到边界

> 不违反，但已经走到了 Freeze 边界。
>
> Core Freeze 当初真正保护的是：`route()`（Task → Provider Selection），而不是 Result Metadata。
>
> MetricsRouter.execute() 如果只是 BridgeResult → Result → metadata += server_metrics，我认为属于 **Execution Decoration**，不是 **Routing Logic**。因此方向没问题。
>
> 但是：建议 ADR 增加一句约束：
> **MetricsRouter MUST NOT influence provider selection or routing decisions.**
>
> 以后 `if token_cost > ...` 绝不能改变 `route()`，否则 MetricsRouter 就开始不是 Decoration 而是 Policy。

**采纳**：在 ADR-0019 决策 1 增加约束。

### Q2 dict vs dataclass — ✅ 保持 dict

> V0.9.6 保持 dict。
>
> Server Metrics 不是 Runtime Domain。它来自 Provider。
> - OpenAI: `usage`
> - Anthropic: 可能 `input_tokens` / `output_tokens`
> - Gemini: 未来可能 `cache_hit`
>
> 如果现在定义 `ServerMetrics` dataclass，你马上就开始适配所有 Provider。这是 Provider Domain，不是 Runtime。
>
> 保持 `dict[str, JSON]` 更健康。真正进入 Runtime 的只有 `ExecutionMetrics`——这是 Runtime 自己的模型。

**采纳**：MetricsExtractor 返回 dict（不改）。

### Q3 Pricing 价格表 — ✅ 继续静态，但抽成接口

> 继续静态。但是不要把 Pricing 写成一个 dict。建议抽成接口。
>
> ```python
> PricingProvider  # abstract
> StaticPricing    # default
> ```
>
> 以后如果 pricing.json / GitHub / Remote API，都不用改 Executor。所以不是为了现在，而是隔离 Pricing 来源。

**采纳**：Pricing 抽成 `PricingProvider` 接口 + `StaticPricing` 默认实现。

### Q4 gemini_cli 不支持 token — ✅ 赞同取舍

> 非常赞同你的取舍。千万不要为了 Token 去改 Provider，否则 Core Freeze 马上失效。
>
> 现在：
> - OpenAI: Token + Latency + Cost
> - Gemini CLI: Latency
>
> 完全可以接受。因为 ExecutionMetrics 本来就是 Optional，不是 Guarantee。
> 以后 Gemini 如果支持 JSON，自然补。

**采纳**：gemini_cli / qoder token 为 0（不改）。

### Q5 cost 估算 vs 精确 — ✅ 一定要标注

> 一定要标注。
>
> CLI 不要：`Cost: $0.0021`
> 而是：`Estimated Cost: $0.0021` 或 `≈ $0.0021`
>
> 这是用户预期的问题。不要让用户认为这是账单。

**采纳**：CLI 输出用 "Estimated Cost" 或 "≈ $0.0021"。

### Q6 plan 用 MetricsRouter / ask 用 ScoreRouter — ✅ 合理

> 合理。因为 plan 本来就是 Execution Runtime，ask 更接近 Quick Invoke。
>
> 不会为了统一让 ask 承担 Metrics。
>
> 不过建议 V1.0 最终统一：
> `RuntimeRouter → Decorators`
> 而不是越来越多 MetricsRouter / HistoryRouter / LoggingRouter。
>
> 但 V0.9 不用急。

**采纳**：当前不一致保留；V1.0 方向记录为 RuntimeRouter + Decorators。

### Q7 server_metrics 放 data 还是独立字段 — ✅ 放 data

> 支持现在放 `event.data`，不要新增 `ExecutionEvent.server_metrics` 字段。
>
> ExecutionEvent 应该尽量稳定。否则以后 cache / pricing / gpu / energy / billing 都会想加字段，最后 Event 越来越胖。
>
> 保持 `data` 作为 Extension Point。很好。

**采纳**：server_metrics 放 event.data（不改）。

### Q8 范围 — ✅ 刚好

> 刚好。千万不要现在加 stats / dashboard / cost alarm / pricing update，否则 V0.9.6 主题就散了。

**采纳**：V0.9.6 范围不变。

## ChatGPT 真正担心的一点（架构风险提醒）

> 这一版唯一让我有一点警惕的是：**Router 正在慢慢承担 Execution Enhancement。**
>
> 目前只有 server_metrics 没问题。但是如果 V0.9.7 继续把 trace_id / billing / cache / retry / statistics 全部放 MetricsRouter，Router 会越来越胖。

### 建议：明确 MetricsRouter 的临时性质

> 我建议 ADR 提前写一句：
> **MetricsRouter is a temporary compatibility layer caused by the current BridgeResult → Result conversion.**
>
> 也就是说真正长期方案应该是：
> - BridgeResult → Result 保留 raw extension
> - 或 BridgeResult 支持 Metadata Extension
>
> 只是 Core Freeze 现在不能改。这样 V2.0 还有退出路径。

**采纳**：在 ADR-0019 增加 MetricsRouter 临时性质声明 + V2.0 退出路径。

### 建议：ExecutionMetrics vs server_metrics 分层原则

> 我建议 ADR 补充：
> **ExecutionMetrics 是 Runtime 的标准指标；server_metrics 是 Provider 的原始指标。ExecutionMetrics 可以由 server_metrics 派生，但 Runtime 不应依赖某一 Provider 的原始字段。**
>
> ```
> server_metrics → ExecutionMetrics → Statistics
> ```
>
> 不要以后 Statistics 直接读取 `server_metrics["prompt_tokens"]`，否则 Runtime 又开始知道 OpenAI。

**采纳**：在 ADR-0019 增加分层原则。

### 对 V1.0 的建议

> V1.0 已经越来越清楚：
> ```
> ExecutionEvent → ExecutionMetrics → Statistics → Workflow Runtime
> ```
>
> Workflow 应该消费 Runtime Metrics，而不是 Provider。

**采纳**：V1.0 方向记录。

> **架构风险警惕**
