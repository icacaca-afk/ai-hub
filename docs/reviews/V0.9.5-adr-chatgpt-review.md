## 总体结论

> ADR-0018：APPROVED（Proposed）
> 评分：10.0 / 10
>
> 这是我认为 V0.9.x 最应该做的一步。
> 原因不是 SQLite，而是它终于完成了 Runtime 三层：
>
> ```
> Execution
>     │
>     ▼
> Event
>     │
>     ├── Memory Consumer
>     ├── SQLite Consumer
>     ├── Future Metrics
>     ├── Future UI
>     └── Future Remote Export
> ```
>
> 整个方向没有偏。

### 最大优点

> 其实不是 SQLite。
> 而是：**Storage 终于成为 Consumer，而不是 Runtime 的组成部分。**
>
> 这是一个非常重要的区别。
> 如果今天是 `Executor → SQLite`，以后 JSON/CSV/Remote/Cloud 都会侵入 Executor。
> 而现在 `Executor → ExecutionEvent → Consumer`，以后新增任何 Storage 根本不用碰 Runtime。
> 这是我最希望看到的。

## 逐项反馈（8 个确认问题）

### Q1 单表 vs 多表 — ✅ 坚持单表

> 坚持单表。不要提前规范化。
> 因为现在真正的实体只有 ExecutionEvent。不是 Plan，不是 ExecutionRecord，不是 Workflow。
> SQLite 只是保存 Event。所以 execution_events 一张表就够。
> 以后 ExecutionRecord 真正成熟再 Materialize。
> 这是典型的 Schema Driven Design，不是 Domain Driven。

**结论**：单表维持。

### Q2 同步 INSERT — ✅ 赞同

> 我赞同。现在一次 Plan 10 Event 左右，SQLite 一次 INSERT 几百微秒，CLI 根本感觉不到。
> 如果为了"未来"加入后台线程 Queue/Flush/Shutdown/Retry/Lock，复杂度远大于收益。
> 坚持 V0.9.x 同步。
>
> 什么时候升级？不是 Event 数，而是真正出现：
> Runtime Daemon / Concurrent Execution / Streaming，再升级。

**结论**：同步 INSERT 维持。升级触发条件更新为 Daemon/并发/流式。

### Q3 长连接 — ✅ 完全赞同，建议加 Context Manager

> 我完全赞同。而且 SQLite 官方推荐也是复用连接。
> 唯一建议：最好 SQLiteExecutionStore 实现 Context Manager。
> ```python
> with SQLiteExecutionStore(...) as store:
>     ...
> ```
> 即使 CLI 现在不用，以后生命周期会非常自然。

**采纳**：加 `__enter__` / `__exit__`。

### Q4 DB 路径 — ⚠️ 调整：workspace 优先，非 HOME

> 我不太赞同 ~/.ai-hub/execution.db 作为默认。
> 我更倾向 Runtime 应该有 Workspace：`project/.ai-hub/execution.db`
> 原因：否则 Project A/B/C 全部混在一起，History 会越来越难解释。
>
> 优先级：1. AI_HUB_DB_PATH → 2. 当前 workspace → 3. HOME

**采纳**：DB 路径改为 workspace 优先（`./.ai-hub/execution.db`）。

### Q5 history vs trace — ✅ 名字好，职责清晰

> 名字很好，而且职责非常清晰。
> 我甚至建议：以后不要再新增 events/logs/timeline/history2。
> 保持：trace = 当前运行，history = 历史运行。用户很好理解。

**结论**：命名维持。

### Q6 INSERT OR REPLACE — ⚠️ 关键调整：普通 INSERT + Warning

> 不要 REPLACE。如果 ExecutionEvent 是 Immutable，那么 INSERT OR IGNORE 更符合语义。
> 甚至我更倾向普通 INSERT。如果违反 PRIMARY KEY，直接记录 Warning。
> 因为 UUID 重复本来就是异常。REPLACE 反而掩盖 Bug。
>
> 排序：INSERT ★★★★★ > INSERT OR IGNORE ★★★★☆ > REPLACE ★

**采纳**：改为普通 INSERT + IntegrityError 时 Warning log。

### Q7 GROUP BY vs plans 表 — ✅ 坚持 GROUP BY

> 坚持 GROUP BY。Plan 目前不是持久化实体，只是 Event 聚合出来的视图。
> `SELECT plan_id, MIN(timestamp), MAX(timestamp), COUNT(*) GROUP BY plan_id` 完全足够。
> 以后 ExecutionRecord 成熟再 Materialize。不要为了"查询方便"提前建 plans。

**结论**：GROUP BY 维持。

### Q8 范围是否保守 — ✅ 一点都不保守

> 一点都不保守。事实上如果这一版再加入 cleanup/TTL/async/token/cost/ExecutionRecord，
> 反而会失去主题。V0.9.5 主题应该只有一句：Execution Event 持久化。整个版本非常聚焦。

**结论**：范围维持。

## 补充建议

### Storage Failure Policy

> 我建议增加 Storage Failure Policy。
> 如果 SQLite 出现 Disk Full / Permission Denied / Busy / Corrupted，怎么办？
> 我建议明确：**Storage Failure ≠ Execution Failure**。
> Runtime 应该继续。最多 Log。不要因为 History 失败导致 Plan 失败。

**采纳**：ADR 新增 Storage Failure Policy 小节。handler 内 try/except 捕获，不 re-raise。

### 未来建议：所有 Query 围绕 Event

> 既然 ExecutionEvent 已经进入 SQLite，我建议以后所有 Query 都围绕 Event。
> 例如不要 `get_plan(...)`，而是 `query_events(...)`。
> History / Timeline / Statistics 全部由 Event 派生。
> 这样 ExecutionStore 始终只是 Event Store，不是 Workflow Store。

**结论**：记入路线，V0.9.7 Statistics 实施时遵循。
